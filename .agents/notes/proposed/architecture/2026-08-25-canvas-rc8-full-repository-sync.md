# Agent Note: Canvas rc.8 full repository sync

Status: proposed

## Problem

Canvas follows the rc.8 Client renderer and module-bootstrap APIs, but compatibility with selected APIs does not prove that the private repository contains the complete official rc.8 package, build, lockfile, generated-output, and runtime behavior. Keeping the private line on rc.7 release metadata also makes package consumers and release tooling describe a different baseline than the code targets.

## Proposal

Merge official commit `141eb6fef83422698aef7a981029e843e8161534` through Git ancestry from the shared rc.7 base. Official rc.8 behavior remains authoritative for build profiles, Client cancellation, reference discovery, branding, attachments, browser handoff, package versions, and release tooling. The merge retains private Canvas packages and their required extensions: Canvas Remote assembly, request-local interaction preparation, projection visibility generations, Canvas Host composition, and the `ui-canvas` dynamic roster entry.

The repository uses `0.1.0-rc.8` for every private dsh package, including Canvas-only packages. The merged manifest graph owns the lockfile; the pinned pnpm version must accept it in frozen mode.

## Alternatives considered

**Continue a selective compatibility backport.** This keeps the change smaller but cannot establish the official commit as an ancestor or reconcile release-wide build and package behavior, so N11.5 would remain `SYNC INCOMPLETE`.

**Replace the private tree with the official tree and re-add Canvas later.** This provides a clean upstream snapshot but discards validated private behavior and makes its recovery dependent on an unverified second migration.

**Copy official files without merging Git ancestry.** Matching selected blobs does not identify the complete release input and leaves future merges unable to distinguish upstream history from private reimplementation.

## Acceptance criteria

- The official rc.8 target is an ancestor of the sync head, and every dsh manifest reports `0.1.0-rc.8`.
- Frozen installation, Host build, Client build, static checks, and documentation checks pass from the exact sync head.
- REAL Web composition boots the complete roster, hands the mount point to `ui-renderer`, keeps Canvas available, and disposes the application root with plugin lifetime.
- Generated catalogs and release artifacts are regenerated by the merged repository toolchain rather than accepted from conflict resolution alone.

## Risks

The merge combines two long-running lines and can preserve individually valid code that no longer agrees at a cross-package API. Compilation and assembled lifecycle evidence therefore remain mandatory; conflict-free text is not validation. Official product branding and the private Canvas view also occupy independent dynamic slots, so composition must retain both instead of choosing one package family.
