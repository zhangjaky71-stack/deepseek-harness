## Current private-tree evidence

The current private repository cannot honestly be called an rc.8 final-tree sync:

1. root `package.json` still declares `0.1.0-rc.7`;
2. `packages/client/ui-renderer` is absent;
3. `packages/client/web/src/boot.tsx` still imports and calls ReactDOM `createRoot()` directly;
4. private Web boot still owns the `AppRoot` settled/loading gate;
5. private Web boot still registers a shell-owned `APP_SHELL_ID` assembly and calls `appShell.renderApp()` for the final application.

This differs materially from official rc.8 root ownership. It is not a cosmetic version-number mismatch.

Historical `sync/upstream-rc8*` branches currently converge on/contain ancestor `ac5a30aadf71571f38e9e2c4c476aa3bca55a59a`, and the current Canvas stack is hundreds of commits ahead with 0 behind. That ancestry proves previous sync/backport activity occurred. It does **not** prove official rc.8 final tree is present, because the mechanically observable rc.7/root-owner differences above remain.

## Canvas compatibility overlay already absorbed

The audit also confirms substantial rc.8-compatible Canvas work is already in the current stack and should be retained during the eventual full sync.

### Dynamic client public boundary

Commit `83dad93af0450a5b49d3db76fe36eba47820e176` (`refactor(ui-canvas): align client surface with rc.8`) moved the Canvas client to the rc.8 export/store discipline.

Current `packages/client/ui-canvas/src/client/index.ts` has runtime exports only for:

```text
apply
inject
```

Canvas components, stores, pure helpers, and state builders are package internals. Shared contracts leave through type-only exports/declaration merges.

N11.5 adds `rc8-contract.client.spec.ts` to pin that runtime public boundary.

### Generic shell ownership

Current Canvas contributes itself dynamically through:

```text
featureCtx.slots.inject('shell.main', ...)
```

Current `ui-layout/AppFrame.tsx` renders only generic regions, including:

```text
renderSlot('shell.main', {})
```

It does not import `ui-canvas`, `CanvasView`, or Canvas Domain types. Conversation remains an independent column/owner and Canvas does not create a second Composer.

N11.5 adds `packages/bundle/web-app/tests/canvas-client-ownership.spec.ts` to mechanically pin this boundary. The stale roster-test description “conversation-view plugin” was corrected to “dynamic Canvas product-surface plugin”; the actual roster assertion remains one ui-canvas row + workspace dependency.

### Lifecycle/state discipline

Current Canvas local state follows rc.8-style responsibility separation:

- mode and semantic selection are stable browser-local observables because prompt preparation also reads them;
- render receives those sources through the reserved `hooks` compartment;
- Editor Draft/save status/Undo/Redo/Clipboard/local positions use the slot-declared store;
- session catalog pruning and plugin dispose clear local mode/interaction state;
- `shell.main` contribution leaves with the plugin/declaration lifecycle;
- semantic/durable Canvas truth stays in Session events and Projection.

### Host-authoritative adjunct services

The current overlay also avoids private Browser truth for:

- deployment settings (`ctx.settings` / Settings scope);
- effective capabilities (`remote.canvasFeatures`);
- Media Node Registry catalog and revision;
- Canvas semantic state and layout Projection.

## Why this remediation PR does not perform the full mechanical sync

The remaining gap is a repository-wide upstream migration, not a Canvas-local patch. Correct completion requires importing/reconciling the official rc.8 package graph and root lifecycle together, including at least:

- `packages/client/ui-renderer` and its roster/dependencies;
- official framework-free Web BootPage flow;
- `uiRenderer` mount handoff and HMR/remount lifetime;
- removal/reconciliation of private AppRoot/AppShell ownership;
- package versions and manifests;
- build/tsconfig/bundle graph;
- generated and lockfile outputs produced by the repository toolchain;
- private three-column/product overlay reapplication on top of the official ownership;
- REAL assembled boot verification.

Attempting to reproduce that migration as scattered contents-API edits without a runnable package manager/toolchain would be more dangerous than leaving the status explicitly blocked: it could create a tree that looks rc.8-shaped but has inconsistent lock/generated/build state.

N11.5 therefore records the precise blocker and prevents false completion rather than manufacturing a partial mechanical sync.
