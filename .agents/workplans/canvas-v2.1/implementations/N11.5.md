# N11.5 implementation — Harness rc.8 compatibility boundary

Status: `BLOCKED / REVIEW`

Primary evidence PR branch: `fix/canvas-n11-5-v2.2-rc8-compatibility` / PR #40

Root/bootstrap remediation branch: `fix/canvas-n11-5-v2.2-rc8-renderer-root`

Stack base: `fix/canvas-n11-v2.2-editor-workspace` / PR #39

## Official target

Official repository: `deepseek-ai/deepseek-harness`

Official rc.8 release merge:

```text
141eb6fef83422698aef7a981029e843e8161534
```

The official tree establishes two Client lifecycle changes that matter directly to Canvas:

1. React root ownership belongs to dynamic `@deepseek-ai/dsh-client-ui-renderer`, exposed through `ctx.uiRenderer.mount(container)`.
2. Host HTML installs `window.__ModuleLoader__`, parser-preloads the modules/runtime client bundles, and Web boot creates the module system through the facade rather than through `window.__DSH_MODULES__` and a shell-static modules package.

## Historical sync evidence is not completion evidence

Historical `sync/upstream-rc8*` refs are ancestors of the current Canvas stack, but the reachable sync anchor still reports the private root as `0.1.0-rc.7`. Those refs prove earlier backport/sync activity, not an official final-tree match.

N11.5 therefore separates:

```text
Canvas / Client compatibility remediation
!=
repository-wide rc.8 release synchronization
```

## Compatibility work already present before this remediation

The Canvas stack already followed the important public rc.8 plugin rules:

- `@deepseek-ai/dsh-client-ui-canvas/client` exposes only `apply` / `inject` at runtime;
- Canvas contributes dynamically through generic `shell.main`;
- `ui-layout` owns generic shell layout, not Canvas business state;
- Conversation owns Conversation/Composer independently;
- mode/semantic selection are stable observable sources used by both UI and prompt preparation;
- Editor Draft/save/Undo/Redo/Clipboard/local layout state is presentation-only;
- durable Workflow/Run/Asset truth stays in Session Projection;
- Settings, effective capabilities and Media Node Registry stay Host/framework authoritative.

The N11.5 compatibility PR (#40) added static/runtime gates for those boundaries and corrected the stale built-client Node Catalog fixture to `{ revision, entries }`.

## Renderer-root remediation completed on the follow-up branch

### Dynamic UI renderer package

Added `packages/client/ui-renderer` as `@deepseek-ai/dsh-client-ui-renderer`.

It now owns:

- React `createRoot` / `hydrateRoot`;
- installation of the slot renderer;
- the sole application-level `renderSlot('root')` assembly;
- selected-session browser-title projection;
- `ctx.uiRenderer.mount(container)` and its React unmount disposer.

Large renderer internals that were already present in private `web-react` with byte-identical rc.8 content were reused as Git blobs rather than manually rewritten. The new package has its own tests and bilingual README contract.

### Framework-free Web handoff

Removed the rc.7 shell-owned files:

- `AppRoot.tsx` / `AppRoot.module.css`;
- `app-shell.ts`;
- `app.tsx`;
- Web-owned `DocumentTitle.tsx`;
- `boot.tsx` React-root boot flow.

Current `packages/client/web/src/boot.ts` is framework-free. After the dynamic graph reaches ACTIVE it requires `uiRenderer` to exist, then mounts through a dependency fiber:

```text
ctx.inject(['uiRenderer'])
  -> uiRenderer.mount(container)
```

The explicit pre-check makes an accidentally missing renderer a loud BootPage failure instead of an unbounded inject wait. The dependency fiber still preserves remount/unmount lifecycle when the renderer service changes.

`ui-renderer` is now present in:

- `packages/bundle/web-app/cordis.patch.yml`;
- `@deepseek-ai/dsh-web-app` workspace dependencies;
- `tsconfig.client.json` project references.

A static ownership gate forbids Web boot from reintroducing React imports, `createRoot`, `hydrateRoot`, `AppRoot`, `appShell`, or `APP_SHELL_ID`.

## rc.8 module bootstrap remediation completed

The private `client-modules` package was verified to be the official rc.7 implementation before migration, so its protocol core could be upgraded without overwriting Canvas-specific logic.

The following private files now have the exact official rc.8 content hashes:

```text
packages/client/modules/src/client/index.ts     c2c6a604c806bfc850b6374ed4d5aaf88e44f845
packages/client/modules/src/client/manifest.ts  cee6679be46dc0ac6c673215d9f667f096e19ef6
packages/client/modules/src/client/system.ts    d4cbb5597b658e06701fd2134c82997a78798e90
packages/client/modules/src/index.ts            a64e879ea3bf256c2f9ef56b17b30dfcbd85db9f
packages/client/modules/src/invariant.ts        00e4e717d546f8a6e5d595c418fb0370b2030406
```

The resulting protocol is:

1. Host HTML installs a queue-mode `window.__ModuleLoader__` facade.
2. Host parser-preloads ordinary `client-modules` and `client-runtime` bundles before the Vite shell.
3. Those scripts only register factories into the queue.
4. Web boot calls `window.__ModuleLoader__.create({ boot, staticModules, ... })`.
5. The facade materializes the modules bootstrap factory with an external-rejecting bootstrap require.
6. `createClientModuleSystem()` retains the bootstrap exports, drains the queue and switches the same facade to live mode.
7. The ordinary modules Cordis graph row later publishes that same closed-over system as `ctx.modules`.

The old `window.__DSH_MODULES__`, shell-static modules registration and `registerStatic(MODULES_ID)` handoff are gone.

The module graph also now carries exact `dsh.client.external` requests, orders dynamic providers before synchronous consumers, normalizes only trailing `/client`, and rejects self-requests/cycles.

The official rc.8 modules regression concepts were migrated with the implementation, covering queue drain, live registration, bootstrap identity, dynamic external arrival, double boot, graph cycles, parser-preload ordering and failure diagnostics.

## Private compatibility intentionally retained

This remediation does **not** pretend the entire private Client build system is now byte-identical to official rc.8.

The private `PLATFORM_MODULES` / client bundle external baseline is currently broader than the final upstream partition. That existing seed surface is intentionally retained while the renderer/root and bootstrap protocols are made compatible. Parser-preloaded runtime satisfies the bootstrap-time runtime arrival requirement; static platform entries continue to answer the private bundle externals already emitted by the current build configuration.

This avoids mixing an unrelated, repository-wide `tsdown.client.ts`/static-linked CSS/build-environment migration into the Canvas N11.5 lifecycle fix without a runnable package-manager/toolchain.

Obsolete Web tests that imported removed rc.7 owner files were deleted only after their assertions were re-homed under `ui-renderer` or framework-free Web boot tests.

## Remaining blockers to a full rc.8 sync claim

The two concrete root/bootstrap architecture gaps are now closed in source. N11.5 is still not accepted because repository-wide release evidence remains incomplete:

1. root and package family versions are still the private rc.7 release line;
2. the wider rc.8 package/build/static-vs-dynamic external graph has not been mechanically reconciled as one release migration;
3. `pnpm-lock.yaml`, generated catalogs and other tool-owned outputs have not been regenerated by the pinned repository toolchain;
4. REAL assembled Web boot has not run against an exact-head built artifact;
5. GitHub Actions remains unable to execute repository steps (`steps=[]`/`steps=null`, log `BlobNotFound`, or enterprise runner queued).

No lockfile or generated artifact is hand-edited to manufacture acceptance.

## Acceptance conclusion

Canvas and the critical Client lifecycle seams are now materially closer to the official rc.8 architecture than the original N11.5 audit recorded: dynamic renderer root ownership and the Host/Web module bootstrap protocol are implemented, tested in source and mechanically guarded.

However, protocol remediation is still not the same as a repository-wide rc.8 release synchronization. Until the remaining package/build/toolchain/REAL-CI evidence exists, N11.5 stays `BLOCKED / REVIEW`, and downstream nodes must not cite it as an accepted rc.8 final-tree baseline.
