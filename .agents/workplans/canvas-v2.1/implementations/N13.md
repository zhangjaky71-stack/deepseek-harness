## Registry implementation

`MediaModelRegistry` is a Cordis Service mounted as `ctx.mediaModels` when installed by a composition.

### Atomic registration

A Provider plugin registers one `MediaProviderDescriptor` with every model it owns. Before commit N13 validates/canonicalizes the complete candidate and rejects:

- invalid Provider/model ids;
- blank display names;
- model/provider ownership mismatch;
- invalid/unsafe execution identity keys;
- empty/duplicate operation lists;
- invalid dimension/duration constraints;
- invalid reference limits;
- invalid/duplicate normalized aspect ratios;
- duplicate Provider ids;
- duplicate `(providerId, modelId)` ids;
- duplicate execution identity keys, both within one candidate and across the live catalog.

A failure commits nothing.

### Effect lifetime / HMR

Registration uses the caller's Cordis effect lifetime. Disposing the owning Provider fiber removes exactly the Provider/models still owned by that registration. Registry revision advances once per successful registration/unregistration.

Change listeners are also effect-scoped and therefore disappear with their caller fiber.

### Non-vetoing change publication

A source audit found an important commit-point bug in the initial implementation: if an `onChange` observer threw after catalog mutation, `register()` could appear to fail even though state was already committed and later observers would be starved.

The final Registry contains each observer failure, logs it, and continues notification. Registry notifications are diagnostics after commit; they are not a transaction veto surface.

Focused coverage proves a failing observer cannot roll back/masquerade a successful registration and cannot prevent a later observer from seeing the revision.

### Snapshot

`snapshot()` returns one immutable synchronous view of Provider/model metadata with deterministic id ordering. The revision is process-local deployment metadata, not durable state and not stable across Host restart.

## Capability descriptor

`MediaModelCapabilities` covers:

- semantic media operation;
- explicit aspect-ratio allowlist or `any`;
- width/height inclusive ranges and steps;
- duration min/max/step;
- maximum reference-image count;
- mask support;
- seed support;
- audio support.

Aspect ratios are reduced to lowest positive integer terms at registration, so `18:32` and `9:16` are identical catalog values.

A second audit strengthened requirement semantics: when width and height are both supplied, the resolver derives their aspect ratio even if the caller omitted `aspectRatio`. An explicit aspect ratio that conflicts with the dimensions is rejected as `MEDIA_MODEL_INVALID_REQUIREMENTS`, preventing a square-only model from being selected for portrait dimensions.

## Resolution behavior

### Strict

Strict mode contains an exact preferred Provider/model and does not carry routing policy.

It fails on:

- unknown preferred model;
- disabled preferred Provider/model;
- capability mismatch.

An incompatible preferred model returns the full mismatch list. Strict never silently switches models.

### Auto

Auto mode requires a caller-owned `MediaModelRoutingPolicy.candidateOrder` and returns the first enabled compatible candidate in that exact order.

The resolver intentionally does not infer preference from registration order, lexical sorting, Provider plugin order, or a hidden global default.

### Fallback

Fallback first keeps its explicit preferred model if it is enabled and compatible. Otherwise it walks the same explicit candidate order as Auto and returns `MEDIA_MODEL_FALLBACK_USED` with preferred/actual references and any known preferred compatibility mismatches.

Duplicate or unknown routing entries fail as policy errors rather than being silently skipped.

### Type-surface correction

The final request API separates strict and policy-selected request shapes so strict callers do not fabricate an irrelevant routing policy.

During source audit another TypeScript issue was found: the discriminant lives at `request.selection.mode`, and TypeScript does not automatically narrow the containing request union from a nested discriminant. The final resolver therefore uses an explicit type guard to narrow `MediaModelResolutionRequest` to `MediaModelPolicyResolutionRequest` before accessing `routing`; no cast is used to hide the issue.

## N12 handoff

Every resolved `MediaModelDescriptor` owns a stable `executionIdentityKey`. A successful N13 resolution returns:

```ts
{
  provider,
  model,
  warnings,
  executionIdentity: { key: model.executionIdentityKey },
}
```

N12 fingerprints and forwards that opaque key but does not choose the model. This preserves the direction:

`requirements/policy → N13 resolution → N12 execution identity`.
