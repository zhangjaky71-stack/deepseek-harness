# N14 Implementation — Media Provider Runtime / Adapter / Mock

Status: **REVIEW**

Branch: `fix/canvas-n14-v2.2-provider-mock`

Stack base: `fix/canvas-n13-v2.2-model-registry` / PR #43

## Scope implemented

N14 adds the Provider runtime role above the N13 model catalog and below N12 execution. The implementation stays Provider-neutral and does not add a real cloud adapter.

### Provider runtime

`@deepseek-ai/dsh-media-provider/runtime` now provides:

- `MediaProvider` semantic runtime interface;
- exact `MediaProviderRuntimeRegistry` mounted as `ctx.mediaProviders`;
- inline, polling, callback, resume, and cancel operation forms;
- serializable opaque async operation handles for later N16/N22 retention;
- Provider-neutral error codes and normalization;
- defensive completion snapshots that detach Provider-owned bytes;
- automatic abort cancellation with sync/async cancellation failure containment.

`MediaProviderRuntimeRegistry` requires `mediaModels` when the service activates and captures that N13 authority. Provider adapter registrations remain effects owned by the caller fiber. This avoids making every adapter-registration caller inject `mediaModels` merely because Cordis service tracing binds service calls to the caller context.

A runtime adapter cannot register until its Provider descriptor exists in N13. The package invariant independently checks the same catalog/runtime relation against reconstructed composition state.

### ProviderExecutor bridge

The generic N14 bridge registers N12 executors for the V1 Provider-backed built-ins:

- `image.generate@1`;
- `image.edit@1`;
- `video.generate@1`;
- `video.image-to-video@1`.

The bridge consumes the opaque `executionIdentity.key` produced by N13. It does not parse that key; `MediaModelRegistry.getModelByExecutionIdentity()` resolves it to the exact current model descriptor. Stale/missing/disabled identities fail closed.

The bridge converts typed N12 inputs/config into semantic Provider requests. Credentials, endpoint URLs, SDK payloads, and Provider-specific request bodies never enter workflow config or the semantic request vocabulary.

Raw Provider outputs are validated for media kind/count before the output materializer is called. This prevents a malformed Provider response from creating future N17/N21 durable-orphan bytes before N14 reports the invalid result.

`MediaProviderOutputMaterializer` is intentionally the only asset-storage seam in N14. Tests use an in-memory implementation. N17/N21 own durable attachment/media-asset validation and storage; N14 does not implement or bypass those nodes.

### Cancellation / resumable operations

For asynchronous operations, `runMediaProviderOperation()` retains one opaque `(providerId, mode, providerTaskId)` handle. Abort requests Provider cancellation exactly once, does not pass the already-aborted signal into the cancellation request, contains both synchronous throws and asynchronous cancellation rejection, waits for that cancellation request to settle, then rejects the caller with `MEDIA_PROVIDER_ABORTED`.

Explicit `cancelMediaProviderOperation()` remains separate for future N16/N22 reconciliation paths and reports normalized cancellation failures to its caller.

### Mock Provider

A new opt-in package, `@deepseek-ai/dsh-media-provider-mock`, registers one universal N13 model and one N14 runtime adapter. It is not added to any shipped profile.

The Mock supports:

- text-to-image;
- image-edit;
- text-to-video;
- image-to-video;
- inline, polling, and callback-style resumable modes;
- deterministic Host-local bytes;
- queued delay/failure scenarios;
- 429, 503, rejection, timeout, abort, and cancellation paths;
- duplicate resume/completion idempotency.

The fixture intentionally does not emulate real credentials, billing, quota, moderation, endpoint/network behavior, or valid production media bytes.

Focused tests cover:

## Acceptance blockers

N14 remains `REVIEW` until repository-pinned validation actually executes on this exact head.

1. N13 and N14 introduce new workspace packages/importer edges. The repository-pinned pnpm toolchain must regenerate and validate `pnpm-lock.yaml`; generated lockfiles are deliberately not hand-edited.
2. Exact-head typecheck, lint, build, focused tests, coverage, package-doc/invariant gates, and built-LIB smokes must run.
3. The surrounding Canvas stack currently has a GitHub Actions infrastructure failure mode where jobs can fail before any project step (`steps=[]`, log endpoint `BlobNotFound`) while enterprise Node24 jobs remain queued. Such failures are neither N14 success evidence nor N14 assertion failures.
4. N17/N21 must later provide the real durable materializer implementation. N14 only defines and tests the seam.
5. N15/N16 still own admission and durable Run/Job lifecycle; Provider compatibility/runtime availability alone is not permission to start a paid or long-running task.

## Acceptance conclusion

The N14 source/API/test/document implementation is complete enough for review, but the node is **not accepted**. It remains **REVIEW** pending pinned lockfile/toolchain regeneration and runnable exact-head repository CI.
