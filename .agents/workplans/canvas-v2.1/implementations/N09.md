## Gap found during rc.8 review

The prior N09 record described the Schemastery Cordis plugin `Config` as deployment truth, but the current repository has a formal settings authority:

```text
ctx.settings.register(namespace, schema, { base, applies })
  schema defaults -> composition base -> durable user document
```

Browser configuration surfaces consume the same namespace through `ctx.settingsScope.bind()`. Feature-owned settings UI contributes through `settings.section`; the settings shell does not own feature policy.

A second lifecycle issue matters for restart-applied policy: base bundle row order carries no activation semantics. If Canvas treated Settings as an optional late service, it could publish base-only capabilities and then mutate them when Settings appeared. Existing Browser consumers intentionally snapshot current capabilities during activation, so that would create a half-live deployment state. The remediation therefore makes Settings a real activation dependency of `CanvasFeatureService`.

## Remediation delivered

### Deterministic Host settings namespace

`CanvasFeatureService` now exports the Host namespace identity `canvas`, keeps its existing Schemastery `Config` as the schema/default contract, and declares:

```text
static inject = ['settings']
```

The shipped `dsh-base` already mounts Settings in every profile. Cordis therefore delays `CanvasFeatureService` activation until the Settings provider is available. The service registers:

```text
settingsNamespace('canvas')
CanvasFeatureService.Config
base = compositionConfig
applies = 'restart'
```

and samples `scope.get()` exactly once into immutable `capabilities` for that service activation. The namespace registration follows the feature-service fiber, so disposal removes it; a later Host restart or dependency/service remount re-registers and re-samples the durable user layer.

Custom compositions that do not need deployment feature policy may omit `CanvasFeatureService`; the Canvas Domain itself does not become the owner of Settings persistence merely because this policy service depends on it.

### Restart semantics

A settings document edit is durable immediately, but it does not silently rewrite the capability surface of an already-running Host. The current activation continues to expose and enforce its sampled `ctx.canvasFeatures.capabilities`; a later Host start or feature-service remount resolves the updated user layer.

This avoids adding a partial live-reconfiguration protocol to N09. Live capability replacement would also require atomic Canvas surface teardown/republication, editor catalog refresh, prompt-preparation replacement, in-flight admission semantics, and future Tool advertisement updates. Those mechanics are not introduced implicitly by a checkbox.

### Browser Canvas settings surface

`ui-canvas` optionally integrates with the current settings UI contract without making the Settings presentation package a requirement for the Canvas main surface:

- the settings contribution waits on `settingsScope + connection + remote` independently from `remote.canvasFeatures`;
- it binds namespace `canvas` through `ctx.settingsScope.bind<CanvasFeatureConfig>()`;
- it registers a feature-owned `settings.section` entry with id `canvas`, independent from `canvas.enabled`;
- the section renders all eight feature flags, raw user-override versus inherited state, read-only/unavailable states, and explicit restart-required copy;
- writes route only through `SettingsScope.set(feature, { enabled })`; Reset uses `SettingsScope.unset(feature)` so the value re-inherits composition/schema layers;
- reactive scope state is passed through the slot `inject.hooks` compartment and framework-generated `useSettings`; the React component owns no subscription machinery or service object;
- the current Canvas product surface still uses only the Host `canvasFeatures` Remote and never treats the Settings checkbox as current-runtime capability authority.

`@deepseek-ai/dsh-client-ui-settings` is an optional client peer/type dependency for this contribution; if that browser service is not present, Canvas rendering continues through its existing dependencies and simply publishes no Canvas-specific Settings section.

## Security and authority conclusions

Feature policy remains deployment state, not Canvas business state. No settings flag enters `CanvasSnapshot`, `MediaWorkflow`, `canvas/change`, layout events, Session Projection, or Browser local persistence.

Authorization and feature policy remain independent. UI hiding is not enforcement. Current Host entry points continue to use the same `ctx.canvasFeatures` checks, and future Agent Tools must advertise the current Host capability and re-check on execution.

The Canvas settings namespace contains booleans only. Provider credentials/secrets remain outside it; the settings wire is still invoked with redaction by the generic surface.

## Generated/lockfile boundary

The remediation introduces real workspace dependency edges to `@deepseek-ai/dsh-settings` and the optional client settings contract. `pnpm-lock.yaml` and generated Typert/client artifacts are not hand-edited. They must be regenerated by the repository-pinned toolchain when a functional runner is available.
