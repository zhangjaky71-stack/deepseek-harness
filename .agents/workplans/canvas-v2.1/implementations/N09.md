## Architecture decisions

Feature policy is deployment state, not Canvas business state. No feature switch is stored in `CanvasSnapshot`, `MediaWorkflow`, `canvas/change`, layout events, or Session Projection. Restarting with different feature config changes what the deployment may do without rewriting historical facts.

Authorization and feature policy remain independent. Authorization answers whether an actor is allowed to perform an action; `ctx.canvasFeatures` answers whether this deployment currently offers that capability. Current Canvas entry points authorize first and only then apply feature policy before any commit or gated query.

The shipped `dsh-base` composition always mounts `canvas-features`; this is the production deployment truth. Direct custom/pre-N09 test compositions that intentionally omit the service retain pre-N09 behavior, which is also useful for constructing historical state in compatibility tests. New shipped consumers must not use service absence as an enable-all feature decision: Browser UI, Canvas interaction, future Agent tools, and future run admission consume the mounted service.

Historical disabled data stays readable. Disabling Video cannot make an old Session undecodable or hide its nodes/results. The policy distinguishes introducing/using a disabled capability from removing or replacing old unsupported state.

Feature flags cannot fabricate implementation. `video.enabled=true`, for example, does not create a provider, storage route, or run engine that has not landed yet. N09 freezes capability vocabulary and enforcement seams; N10+ own node/runtime implementation.
